# T-Display K230 RootFS Policy

This document defines the current root filesystem policy.

Chinese version:

- [rootfs.zh-CN.md](rootfs.zh-CN.md)

## Scope

The TDVP rootfs is a minimal Buildroot-generated Linux userspace for the
T-Display K230 platform.

It must support:

- BusyBox init and shell utilities;
- serial bring-up;
- platform init scripts;
- BSP/runtime libraries and services;
- validation tools explicitly selected by the platform.

It must not become:

- a desktop system;
- a Debian/Ubuntu-like runtime;
- a target-side package-managed environment;
- a dump of the full reference SDK demo rootfs;
- an application-specific filesystem.

## Current Baseline

The rootfs must be adapted with the selected `k230_linux_sdk` baseline.

The SDK may provide useful rootfs structure and package references, but TDVP
must classify each imported package:

| Class | Rule |
| --- | --- |
| platform-required | allowed in the base image |
| validation-only | allowed during bring-up, removable later |
| demo-only | not part of the base image |
| rejected | not imported |

The current bring-up `validation-only` set includes:

- Dropbear, only as an SSH/debug control plane used with `eth0` DHCP; root
  password is fixed to `tdvp`;
- `ethtool`, `iperf3`, `tcpdump`, `strace`, and `lsof` for network and system
  diagnostics;
- `v4l2-ctl` and `media-ctl` for camera/media graph validation;
- `aplay/arecord`, `amixer`, and `speaker-test` for audio/speaker validation;
- `spi-tools` and `spidev_test` for SPI wiring validation.

These tools do not change the platform API boundary. Applications still must
not depend directly on SSH, V4L2, ALSA, SPI, evdev, sysfs, or ioctl.

## Required Contents

Minimum expected contents:

```text
/bin
/sbin
/lib
/usr/bin
/usr/lib
/etc/init.d
/etc/vision-platform
/opt/vision
/proc
/sys
/dev
/tmp
/var
```

Required behavior:

- devtmpfs provides device nodes;
- init reaches the platform startup path;
- no target package installation is required after flashing;
- app code does not require manual files copied into the rootfs.

## Overlay Rules

Rootfs overlay is for small platform-owned files only:

- init scripts;
- platform config;
- small validation assets.

Do not use rootfs overlay for:

- large binaries;
- generated files;
- vendor demo dumps;
- app-specific state;
- private developer convenience files.

## Acceptance

The rootfs is accepted when:

- it is generated by Buildroot from tracked inputs;
- it boots to BusyBox userspace through the selected K230 Linux path;
- platform init runs;
- the base image contains only classified packages;
- when the bring-up/debug control plane is enabled, root password, network
  interface, and scope boundary are documented;
- BSP/runtime APIs remain the only supported application hardware interface.
