# T-Display K230 Boot Policy

This document defines the boot policy for the T-Display K230 Linux platform.
It separates active Linux baseline facts from hardware-reference facts and
historical boot experiments.

Chinese version:

- [boot.zh-CN.md](boot.zh-CN.md)

## Source Order

Boot decisions must be derived in this order:

1. `kendryte/k230_linux_sdk`: primary Linux boot, OpenSBI, U-Boot, environment,
   and image-layout reference.
2. T-Display K230 hardware facts from the LilyGO reference tree and schematic.
3. TDVP policy decisions required to keep the platform minimal and
   API-stable.
4. Historical probe archives, only when re-derived against the current Linux
   baseline.

The LilyGO/CanMV RT flow may provide hardware clues, but it does not define the
Linux platform boot contract.

## Accepted Baseline Inputs

The first Linux boot profile must record:

| Item | Required Record |
| --- | --- |
| K230 Linux SDK revision | exact repository commit |
| Buildroot profile | selected SDK defconfig or board profile |
| kernel source | repository URL and revision |
| kernel defconfig | exact defconfig name |
| device tree | source DTS and TDVP board delta |
| OpenSBI source | source, version, and packaging mode |
| U-Boot source | source, version, board name, and environment policy |
| image layout | partition map, offsets, filesystem types |

No boot artifact is accepted without pinned provenance.

## Rejected As Platform Policy

Do not promote any of the following to TDVP boot policy without a new explicit
decision:

- a non-Linux reference payload as a Linux payload;
- a hidden payload slot inherited from a non-Linux flow;
- a CanMV application partition model as a TDVP application model;
- U-Boot DTS files as Linux kernel DTS files;
- a hand-written local OpenSBI/Linux chain as the first platform baseline;
- a direct boot command that bypasses the selected K230 Linux boot model.

These may remain useful as debugging evidence, but they are not architecture.

## Target Boot Chain

The target Linux boot chain is:

```text
BootROM
  -> first-stage loader / SPL
  -> U-Boot
  -> OpenSBI if required by the selected K230 Linux boot flow
  -> Linux kernel
  -> BusyBox init
  -> TDVP platform init
  -> vision-runtime service or selected SDK demo
```

The exact packaging of SPL, U-Boot, OpenSBI, kernel, DTB, and rootfs is defined
by the selected K230 Linux baseline plus the documented T-Display delta.

## U-Boot Environment Policy

TDVP may own a generated U-Boot environment only after the selected K230 Linux
boot model is understood.

Rules:

- The environment source must be tracked in this repository.
- The binary environment must be generated by Buildroot or a documented build
  step.
- Kernel and DTB load addresses must be inherited from, or justified against,
  the selected K230 Linux SDK profile.
- Manual serial commands are debugging tools, not the platform boot contract.
- `extlinux.conf` may be generated as documentation or fallback only when the
  selected U-Boot path supports it.

## Buildroot Responsibilities

Buildroot is responsible for generating deterministic bootable images from
tracked inputs:

- bootloader artifacts, when selected by the board profile;
- kernel image;
- device tree blobs;
- generated U-Boot environment or boot scripts;
- minimal root filesystem;
- platform init scripts;
- BSP/runtime packages.

Buildroot must not become:

- a target-side package installation workflow;
- a desktop startup system;
- a per-application image generator;
- a place where raw Linux hardware nodes become public application APIs.

## Early Boot Acceptance Criteria

An early Linux image is accepted only when all of these pass:

1. The board boots from the generated SD image.
2. UART reaches Linux kernel logs.
3. UART reaches BusyBox userspace.
4. `/proc/cpuinfo` and kernel logs identify the expected K230/RISC-V target.
5. Rootfs mounts from the generated image without manual target-side edits.
6. Reboot produces the same behavior.
7. Boot details remain below the BSP/runtime/SDK API boundary.

## Hardware Validation Items

These items must be proven on real T-Display K230 hardware:

- SD-card controller numbering used by U-Boot and Linux.
- UART console mapping.
- load addresses for kernel and DTB.
- OpenSBI packaging mode.
- display, camera, input, storage, radio, power, and sensor availability after
  Linux reaches userspace.
